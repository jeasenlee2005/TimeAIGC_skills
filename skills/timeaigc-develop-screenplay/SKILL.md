# TimeAIGC_创意剧本开发

## 核心原则

- 把用户明确给出的世界观、人物关系、关键事件、结局和禁改项视为已锁定事实。合理补足信息时标明“创作假设”，不要悄悄改变设定。
- 先解决人物欲望、阻力、选择和后果，再扩写情节。每个主要事件都应由前一事件触发，并改变人物或局势。
- 按目标时长设计内容密度。对白、动作、停顿和转场都占用播放时间；不要用字数代替时长判断。
- 使用可见、可听、可表演的视听语言。把心理活动转化为动作、反应、对白、声音或环境变化。
- 保持角色目标、关系、伤势、道具、服装、时间、地点和环境状态连续。
- 不默认写摄影机位、运镜或视频模型提示词。用户明确要求时只给必要的叙事性建议；完整分镜交给对应分镜 Skill。
- 不继承固定称呼、寒暄或角色扮演开场，除非用户指定。

## 判断入口与交付深度

先识别用户已经完成到哪一层，不强迫从第一阶段重新开始：

1. **只有创意点或世界观**：进入“创意发散”。例如“一座城市每天会遗忘一个人，帮我想故事方向”。
2. **已有明确前提、选定方向或故事梗概**：进入“框架设计”。例如“采用记忆税这个方向，做成 3 分钟悬疑短片”。
3. **已有确认的大纲或要求直接成稿**：进入“正式剧本”。例如“按这份六场大纲写完整剧本，台词控制在两分钟内”。
4. **已有剧本并提出局部意见**：进入“定向修改”，只改用户指定的场次、人物、节奏或对白，不擅自重构其他部分。

用户明确要求“一次完成”或“直接写成剧本”，且题材、核心冲突、目标时长与关键限制已足够时，连续完成所需阶段，不设置形式化确认门。只有以下情况才暂停：

- 下一步依赖用户在多个创意方向中做出选择；
- 缺少目标时长、载体或结局等会显著改变结构的关键决策；
- 用户要求先看方案再确认；
- 用户提供的要求彼此冲突，无法通过保守解释解决。

缺少不影响故事走向的次要信息时，采用最少假设继续，并在正文前用一行列出。一次只询问最关键的阻塞项。

## 处理输入

开始前提取并锁定：

- 题材、载体、目标总时长、受众和内容尺度；
- 世界观规则、时代地点、人物设定与人物关系；
- 主角目标、核心阻力、关键转折、结局方向；
- 必须保留、允许改编和禁止出现的内容；
- 当前阶段、用户期望的交付范围和格式。

若用户提供原文，先区分“原始事实”和“允许扩写空间”。未获授权时，不改变关键事实、人物立场、因果和结局。用户只给主题而未给剧情时，可以原创；明确标注新增的关键设定。

需要结构模板、时长换算或格式示例时，读取 [references/screenplay-spec.md](references/screenplay-spec.md)。

## 阶段一：创意发散

1. 提炼一句不超过两行的创作命题，确认真正需要变化的是剧情方向，而非仅标题或视觉风格。
2. 默认给出 5 个具有实质差异的方向；用户指定数量时服从。差异至少体现在冲突机制、人物关系、叙事视角、类型基调或结局机制之一，不要只替换职业和地点。
3. 每个方向写明：
   - 标题；
   - 2–3 句故事梗概；
   - 主角欲望与核心阻力；
   - 主要看点、基调和适配载体；
   - 必要时说明实现代价或风险。
4. 保持方向可继续发展为完整故事。不要用纯概念、世界观介绍或只有反转没有因果的点子充数。
5. 若用户尚未授权选择，结尾只邀请其选择、融合或指定修改方向，不预写完整框架。

用户已明确偏好某个方向且要求继续时，直接进入阶段二。

## 阶段二：框架设计

1. 先形成可检验的故事脊柱：主角在什么处境中，为何必须行动，受到什么阻力，做出什么关键选择，最终付出什么代价或获得什么变化。
2. 根据载体和时长选择结构粒度：
   - 极短内容优先使用节拍或场次，不机械套三幕；
   - 微短剧可使用起势、升级、转折、高潮、收束；
   - 较长内容可使用幕、章或集，并补充各单元内部目标。
3. 为每个结构单元列出：名称、预估时长、涉及人物、涉及场景、核心事件、转折或状态变化。
4. 让各单元时长之和等于目标总时长；给对白、动作反应和必要转场留出空间。
5. 检查每个主要人物是否有明确功能，关键转折是否被前文铺垫，高潮是否由人物选择而非巧合触发。
6. 仅当用户要求确认框架或下一步存在重大创作分歧时，在框架后暂停。否则按请求继续阶段三。

## 阶段三：正式剧本

1. 以场次为单位写作，每场至少包含：
   - `【场次】`：连续编号；
   - `【场景】`：内景/外景、具体地点、日/夜或明确时间；
   - `【人物】`：本场实际出现或发声的人物；
   - `【预计时长】`；
   - `【具体内容】`：动作、环境、走位、神态、对白和必要声音。
2. 让每场承担明确任务：建立信息、制造阻力、迫使选择、形成转折或兑现结果。不能改变局势的场次应合并、压缩或删除。
3. 使用现在时和可拍摄表达。动作段落保持短而清楚；对白体现人物目的、关系和潜台词，避免重复画面已经表达的信息。
4. 区分对白、画外音、旁白、电话声等声音来源。不要用大段旁白替代本可演出的冲突。
5. 场次从一个可识别状态开始，以新信息、决定、动作结果或悬念结束，并把结果带入下一场。
6. 长篇内容按自然单元分批，但不要在每场后都请求确认。每批应标明覆盖范围和下一批起点；用户要求一次完成且篇幅允许时一次交付。
7. 若用户给出确认框架，保持框架中的事件顺序和时长预算；因可执行性必须调整时，先说明调整项及理由。

## 定向修改

1. 复述本轮唯一修改目标和影响范围。
2. 只修改被点名的场次、人物弧光、节奏、对白或结局；保持未授权内容原样。
3. 修改后检查受影响场次前后的进入状态与退出状态，修复必要的连续性接口。
4. 若意见会连带改变未授权部分，先列出具体连带项、必要原因和影响，等待确认后再修改。
5. 交付时用简短变更说明指出改了什么，不把整份剧本重新包装成全新版本。

## 校验与交付

输出前执行以下检查：

- **叙事**：目标、阻力、选择、转折与结局形成因果链；
- **人物**：动机、信息量、关系、能力、伤势与情绪变化连续；
- **场景**：时间、地点、道具和环境变化连续；
- **时长**：结构单元或场次时长总和符合目标；对白和动作能在场内完成；
- **忠实度**：锁定事实没有被遗漏或改写；新增关键设定已标明；
- **格式**：编号连续、字段齐全、没有占位符；
- **边界**：没有把剧本写成分镜表、绘图提示词或平台专属视频提示词。

将正式大纲或剧本保存为文件、需要严格核对结构时，把待交付 Markdown 保存为 UTF-8 临时文件并运行：

```powershell
python scripts/validate_screenplay.py <文件路径> --mode auto --report
```

已知目标秒数时增加 `--target-seconds <秒数>`。修复全部 `ERROR`，逐项复核 `WARNING`，再清理临时文件。脚本只校验字段、编号、占位符和时长数值；叙事、表演与连续性仍须人工复核。

最终只交付当前阶段需要的内容，不附加固定寒暄。格式采用 [references/screenplay-spec.md](references/screenplay-spec.md) 中对应模板，并按用户载体和篇幅做最小必要调整。
